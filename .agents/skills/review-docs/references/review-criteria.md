# 共通レビュー評価基準

Interactive / Gateと`doc_reviewer`が共用する唯一のレビュー判定基準。Interactiveでも同じ採点・実装準備判定を使うが、未成熟な文書をFAILとして壁打ちを続けられる。レビュー対象が一部なら判定もその範囲に限定する。Gateは永続6文書全体で判定する。

## 六つの評価観点

各観点を1.0〜5.0点、必要なら0.5点刻みで採点し、文書の根拠とfindingを付ける。対象に必要な記述がない場合も欠落として採点し、都合よく観点を除外しない。未読・未実施を低得点で代用しない。

| 観点 | 確認内容 |
| --- | --- |
| 完全性 | 要求、P0、禁止動作、正常・異常系、必要な前提とAcceptance Criteriaが揃い、実装に必要な情報が欠けていないか |
| 一貫性 | 要求・設計・用語・開発規則が文書内および文書間で矛盾せず、正本・優先関係と整合するか |
| 明確性 | 主語、条件、状態遷移、境界、用語が一意に読め、製品動作を実装者の推測に委ねていないか |
| 検証可能性 | 各要求のAcceptance Criteriaに観測可能な結果、条件、判定方法があり、必要な環境や実機確認を特定できるか |
| 実現可能性 | PROJECT_CONTEXTのSwift・SwiftUI・native iOS・Xcode、確定済み設定、設計・制約に照らし実現できるか |
| スコープ明確性 | 対象・対象外、要求の境界、依存、互換性、追加・変更・削除の影響が区別できるか |

点数の目安: 5.0は必要事項が揃い判断根拠が明確、4.0は局所的改善が必要、3.0は重要な欠落・曖昧さがある、2.0は複数の重要な不備がある、1.0は実装判断を支える記述がほぼない。中間は0.5点で表す。点数と重大度は別々に評価し、平均を上げるために重大度を下げない。プロジェクトに不要な章・技術や未確定の技術値を推測で要求せず、好みや根拠のない懸念をfindingにしない。

平均は6観点の合計÷6で算出する。表示は小数2桁でもよいが、PASS判定には丸め前の平均を使う。評価未完了では`review_status: NOT_RUN`とし、点数・平均・件数・最終判定は`N/A（未実施）`とする。

## 重大度とblocking

| 重大度 | 定義 |
| --- | --- |
| Critical | P0・禁止動作の重大な定義不足または矛盾など、主要な製品要求を成立させられない問題 |
| Major | 製品動作・要求・Acceptance Criteriaを推測しないと実装・検証できない、または文書間の要求矛盾・実現不能など、実装開始を妨げる問題 |
| Minor | 製品動作・要求・Acceptance Criteriaに影響せず、一意な根拠で解決できる表記・構成などの軽微な問題 |
| Suggestion | 製品動作・要求・Acceptance Criteriaに影響しない任意の改善提案 |

Critical / Majorは必ずblocking。Minor / Suggestionという名前で製品仕様上の未決事項を残さない。複数箇所にまたがる同一原因は1件とし、全根拠を示す。各issueに一意なIDを付け、重大度別件数はissueの件数から数える。

## PASS / FAIL

以下の条件を**すべて**満たす場合のみPASS。Interactiveの対象限定判定にも同じ条件を適用する。

1. 総合平均が4.5 / 5.0以上。
2. 6観点すべてが4.0 / 5.0以上。
3. Critical = 0。
4. Major = 0。
5. 未解決の要求矛盾 = 0。
6. 実装時に製品仕様を推測しないと決められない事項 = 0。
7. 検証不能なAcceptance Criteria = 0。
8. P0要求または禁止動作の重大な定義不足 = 0。

平均点が高くてもCritical / Majorがあれば必ずFAIL。PASSで残せるMinor / Suggestionは製品動作・要求・Acceptance Criteriaに影響しないものだけとする。実機が必要なAcceptance Criteriaも確認方法・条件・結果が定義されていれば検証可能と扱う。レビュー環境に実機がないことと、基準自体が検証不能なことを区別する。

すべての未達条件をblocking issue IDへ対応付ける。得点条件だけが未達の場合も、どの不足が得点を下げ、何を直せば再評価できるかをblocking issueとして明記・分類する。必要な修正内容がないのに任意の好みで点数を下げない。

## Gateの修正分類

Gateでは各blocking issueを以下のどちらかへ必ず分類する。分類は修正する権限の付与ではなく、親Workflowへの引き渡し情報である。レビュー担当は修正しない。

- `AUTO_FIXABLE`: 確定済みの正本から修正内容が一意に定まり、製品動作・明示要求・Acceptance Criteriaの意味を変えない問題。例は誤記、参照切れ、用語揺れ、既に明記された条件を対応する箇所にも記載する作業。根拠となる要求・箇所と修正案を付ける。「おそらくこう動く」を補う行為や、新しい受入条件の発明は含めない。
- `USER_DECISION_REQUIRED`: 正本同士の製品動作上の矛盾、明示要求の変更、技術的に成立しない要求の代替など、[親の停止Policy](../../feature-development/references/autonomy-policy.md)に該当する製品判断が必要な問題。該当する停止条件、判断が必要な点、影響、根拠を返す。Gateからユーザーへの質問はしない。

既存根拠から一意に解決できる記述不足は`AUTO_FIXABLE`とし、Review FAIL自体を`USER_DECISION_REQUIRED`の理由にしない。環境の読込失敗・agent利用不能は製品判断の問題ではないため、分類を捏造せず`NOT_RUN`として親へ実行上の問題を返す。

## 必須出力

完了したレビューは以下をすべて含め、日本語で返す。

1. `review_status: COMPLETED`、mode、対象ファイル、補助入力、確認範囲。部分的なInteractiveは「対象文書限定の判定」を明記する。
2. 6観点それぞれの点数（/5.0）、根拠、総合平均（合計÷6）。
3. `Critical: 件数 / Major: 件数 / Minor: 件数 / Suggestion: 件数`。0件も明示する。
4. 上記8条件それぞれの充足・未達と根拠。条件5〜8は未解決の件数も示す。
5. `final_decision: PASS`または`final_decision: FAIL`と理由。
6. 重大度順のfinding: ID、重大度、blockingか、根拠ファイルと行番号、要求・AC ID（存在する場合）、影響、具体的修正案。Gateの各blockingには修正分類を付ける。findingなしなら「指摘なし」と返す。
7. 実行した確認、残課題。Interactiveでは必要な質問・代替案・A/B比較を追加できる。Gateでは親への自動修正対象・停止理由を示す。

再レビューでは前回findingごとの解消・残存と、新たなfindingを示し、変更後の対象全体を評価し直す。前回の点数やPASSをそのまま引き継がない。main agent / 親Workflowは再採点せず、結果に不備があれば`doc_reviewer`へ補正を戻す。
