# 自律判断Policy

`feature-development` と、その実行コンテキストを受け取った子Skillに適用する。Ideas/要件定義の対話や単独Skillの入力契約は置き換えない。

## 判断順序

永続6文書 → P0要求 → 禁止動作 → Acceptance Criteria → AGENTS.md → PROJECT_CONTEXT.md → 既存Architecture → 既存コードのConvention → 後方互換性 → 小さい変更範囲 → 将来変更しやすい可逆的な選択の順で根拠を確認する。

これは合意済み要求を実現する内部判断の順序である。P0、禁止動作、ACは永続文書の制約としてすべて満たす。正本同士の製品動作の矛盾を優先順位だけで消さず、実行環境の権限や上位指示を上書きしない。

実装順序、ファイル・class・関数分割、内部API、内部状態管理、テスト構成、軽微なリファクタリング、Build/Test/Lint failure、Review/Validation指摘への対応はmainが決定する。既存要求から一意に導ける不足の補完、誤字・参照・表記の訂正も追加確認しない。要求・ACの意味、数値、優先度、対象ユーザー、公開動作は推測して補わない。

判断は根拠文書/箇所、選択、影響を対象steeringのdesign/tasklistへ記録する。承認を得るためだけの計画提示はしない。

## ユーザー判断を求める停止条件

次の場合だけ親mainが影響範囲を止め、根拠と必要な判断をまとめて質問する。

- Source of Truth同士が矛盾し、選択によって製品動作が変わる。
- 明示された要求自体の追加・削除・変更が必要で、その変更に合意がない。
- P0要求または禁止動作を満たせない。
- 技術的に要求が成立せず、代替仕様が必要。
- 大規模なArchitecture変更が必要。
- データ消失等の不可逆な操作が必要。
- Security / Privacy上の重大な製品判断が必要。
- 外部サービス、本番環境、課金等へ重大な影響がある。

子Skill・reviewer・validatorはユーザーに直接質問せず、根拠と停止理由を親へ返す。既に合意された変更は再承認を求めない。無回答を承認とみなさず、依存しない安全な調査・作業は継続する。

## 失敗・実行権限との区別

- Build/Test/Lint失敗、Review FAIL、Validation FAIL、内部設計、変更順序、軽微な文書修正は工程承認の理由にしない。原因を調べ、修正と再検証を続ける。
- reviewerの `AUTO_FIXABLE` は文書の根拠から意味を変えずに直せるもの、`USER_DECISION_REQUIRED` は上の停止条件に該当するものとして扱う。判断根拠が欠ける報告は評価者へ返し、親が都合よく分類を書き換えない。
- sandbox/approval、ネットワーク、保護ディレクトリなどの実行制約は維持する。Workflow実行の許可は権限拡張、外部依存の新規導入、署名/Team/Capabilities変更、commit/push/deployの包括許可ではない。必要な権限要求は実行環境の手段に従い、工程承認と区別する。
- 環境不足・入力不足・agent利用不能では成功を捏造しない。安全に復旧できるかを調べ、実行可能な範囲を終え、残る外部阻害と再開条件を記録する。実機でしか確認できないACの扱いはvalidate-implementationの判定契約に従う。
